# 第 6 章：搭起第一个机器人 Agent 循环

前五章已经把环境、观察、坐标和技能接口准备好。本章把它们接成一个能够根据反馈选择下一步的循环。先让每个环节都可检查，再接真实语言模型，才能区分系统问题与模型问题。

前置要求：完成第 2 章安装，能运行固定脚本基线，理解 `move`、`grasp` 与 `release` 的作用。后面的命令均在仓库根目录、已经激活的 Python 虚拟环境中执行。

## 本章目标

完成一次红色方块到蓝色区域的搬运，读懂完整动作记录，并说清楚决策来自哪里。你将得到 `events.jsonl` 和 `summary.json`，能解释一次动作返回与整个任务成功之间的区别。

## 先区分循环与决策器

一个最小循环包含五件事：取得观察，选择动作，检查参数，执行工具，再把结果送回下一轮。循环还需要停止条件，否则一次失败可能变成无限重试。

本课程有两种决策模式。`scripted` 由人工编写的确定性规则决定下一步，用于学习闭环结构；它没有调用大模型，也不能作为语言模型具身能力的证据。`llm` 才把任务、工具说明与反馈发给外部模型，由模型返回工具调用。两者共享教学环境，便于把接口问题与决策差异分开研究。

下面是理解结构的伪代码，不是需要复制执行的实现：

```text
在预算范围内重复：
    读取当前信息
    由规则或模型选择一个工具调用
    检查工具名、参数与允许范围
    执行工具，保存返回值
    检查任务是否完成；完成则结束
预算耗尽或无法继续：记录失败并结束
```

这里最容易遗漏的是“保存返回值”。若抓取失败后仍按原计划搬运，程序虽然调用了很多工具，行动却没有真正受反馈影响。

## 第一步：明确工具能做什么

| 工具 | 输入与作用 | 不能据此推断什么 |
| --- | --- | --- |
| `observe` | 读取当前教学场景状态 | 坐标不是相机识别结果 |
| `move` | 接受世界坐标 `x, y, z`，尝试移动末端 | 到达位置不等于抓到了物体 |
| `grasp` | 尝试建立教学抓取附着 | 返回成功不代表真实摩擦夹持已验证 |
| `release` | 解除附着、放下物体 | 松开不等于放进目标区域 |
| `locate_color` | 按 `block` 或 `goal` 定位受控颜色目标 | 不具备任意物体识别能力 |

上表列出 `World` 教学环境提供的接口；当前在线模型实际只获得 `observe`、`move`、`grasp`、`release` 四个基础工具，`locate_color` 用于第 8 章独立练习，没有注册为在线模型的视觉工具。

本章离线循环使用精确状态观察。简化 SCARA 机械臂通过显式约束附着来模拟抓取，实验重点是接口与反馈；第 8 章才独立研究 RGB 像素如何产生位置估计。

## 第二步：运行确定性闭环

```sh
python lab/run.py agent --mode scripted --seed 7 --out runs/ch06-scripted --perturb none
```

先不要增加扰动。固定种子可以保留一致的初始化条件，单独的输出目录则保留本次证据。观察控制器如何从接近、抓取、搬运走到释放，以及中间何时重新读取状态。

运行后执行下面的完整检查程序。它只读取日志，不控制机器人：

```sh
python - <<'PY'
import json
from pathlib import Path

run = Path("runs/ch06-scripted")
summary = json.loads((run / "summary.json").read_text())
print(json.dumps(summary, ensure_ascii=False, indent=2))
print("\n逐条事件：")
for index, line in enumerate((run / "events.jsonl").read_text().splitlines(), 1):
    event = json.loads(line)
    print(index, json.dumps(event, ensure_ascii=False))
assert summary["mode"] == "scripted"
assert summary["model_calls"] == 0
assert summary["success"] is True, "程序运行结束，但任务验收未通过"
PY
```

`model_calls` 为零是本实验的重要验收信息。`steps` 用来描述执行开销，`success` 才描述任务验收；`error` 则帮助解释异常。不要把“命令正常结束”写成“模型成功完成任务”。

## 第三步：给日志标注因果关系

从记录中挑出第一次抓取，在纸上连出三段证据：抓取前末端和方块处于什么关系，`grasp` 返回了什么，下一步为什么继续或重试。再检查释放之后的场景，找出支持最终成功判断的状态。

这一步是在验证反馈是否真的进入决策。看到动作顺序相同并不能证明没有闭环：在没有扰动时，固定脚本与反馈控制器可能恰好做出相同动作。第 9 章会有意制造失败，让两者的差异显现。

## 第四步：理解真实模型的接入位置

在线模式通过兼容 Chat Completions 的工具调用接口工作。先在本机环境配置 `AF_API_KEY`、`AF_MODEL` 和 `AF_BASE_URL`；基础地址应指向服务的 API 根路径，程序会追加 `/chat/completions`。然后运行：

```sh
python lab/run.py agent --mode llm --seed 7 --out runs/ch06-llm --perturb none
```

不要把密钥写进课程网页、代码仓库或实验截图。网站本身不执行模型请求。本课程首期验证的是离线流程；未配置有效密钥的环境没有完成真实在线模型实测，因此这里不预报在线成功率。

模型应依据工具返回选择下一步；返回普通文字、虚构工具名或无效坐标都不等于执行成功。遇到接口不兼容时，先检查模型是否支持工具调用，以及本地日志中的错误，不能把接口失败计作机器人运动失败。

## 本章验收与排查

验收时交付命令、两个日志文件，以及一段抓取前后证据。你应能回答：用了哪个模式？是否调用模型？观察来自状态还是像素？最终由什么条件验收？

若动作执行但任务失败，先检查抓取反馈和目标位置；若没有任何动作，检查参数、依赖或在线接口错误；若日志里的状态始终不变，检查是否真的执行了工具。每次重跑换一个输出目录，避免混淆记录。
