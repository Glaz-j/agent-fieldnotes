第 07 章 / Agent 闭环

把语言变成可检查的目标

处理指令、歧义与任务完成条件

“把它放好”听起来很自然，却没有告诉机器人“它”是谁、“好”在哪里。即使模型生成一段流畅计划，也不能因此判断任务已经被正确理解。本章把用户指令、目标表示、执行过程和验收条件分开。

前置要求：完成第 6 章离线循环，理解工具参数和 JSON。实验继续使用同一个红色方块与蓝色目标区域，不增加机器人硬件或训练模型。

本章目标

解析一条受支持指令，识别一条需要澄清的指令，把确认后的任务送入控制器，并根据状态而非文字回答验收。最终提交三份证据：解析输出、澄清输出和执行记录。

为什么目标需要独立表示

自然语言面向人，目标对象面向程序。对于“把红色方块放到蓝色区域”，至少需要确定被操作对象、目标区域与完成关系。执行计划则回答怎么实现它，例如接近、抓取、搬运、释放。

目标与计划分开后，即使搬运路线改变，任务仍然相同；即使目标区域移动，程序也应重新查找它，而不是把最初坐标当成任务本身。实体身份是“蓝色区域”，位置只是某次观察得到的属性。

验收还要区分动作结果与最终关系：移动到目标上方、释放成功、方块确实落入目标，是三个不同命题。一个工具返回正常，只能说明它负责的那一步发生了什么。

第一步：解析明确的指令

在仓库根目录、激活第 2 章的环境后运行：

python lab/run.py parse-goal --instruction '把红色方块放到蓝色区域'

阅读完整输出：status 表示解析是否通过，object 指向红方块，target 指向蓝区域，parser 说明解析来自受限规则。完成条件由环境的验收函数定义，不包含在这一小段 JSON 中。这里的解析器只接受明确模板并进行全文匹配，不调用语言模型，也不提供通用中文理解能力。

使用这样的小解析器，是为了先让“输入是否被接受”可以测试。以后替换成模型生成结构化目标，仍然需要校验对象是否存在、关系是否受支持，以及是否有足够信息。JSON 能被解析，只证明格式成立，不能证明语义正确。

当前程序只用 status 控制是否允许执行，object 和 target 用于展示目标表示；控制器和验收函数仍固定为同一个红块到蓝区的任务。修改这两个 JSON 值不会自动增加对象支持，通用目标执行还需要参数化控制器与验收函数。

第二步：让含糊指令停在执行之前

python lab/run.py parse-goal --instruction '把方块放到目标区域'

这条指令没有给出课程要求的颜色信息，应进入 needs_clarification。记录解析器提出的问题，不要手工补成成功结果。真实机器人需要澄清时，控制流程应该等待新输入；一个程序“猜中了”当前唯一物体，不表示它学会了解决指代。

再检查不受支持的对象：

python lab/run.py parse-goal --instruction '把绿色方块放到蓝色区域'

当前场景没有绿色方块。正确的边界是说明缺少对象或需要澄清，不能悄悄把绿色换成红色。解析命令只解释任务，不执行搬运，因此适合用来检查不同输入。

第三步：把已确认任务交给控制器

python lab/run.py agent --mode scripted --seed 7 --instruction '把红色方块放到蓝色区域' --out runs/ch07-goal

任务一旦进入执行，控制器应该围绕已确认的目标行动。先观察，再操作，结束时检查实际状态。用下面的命令查看结果：

python - <<'PY'
import json
from pathlib import Path

summary = json.loads(Path("runs/ch07-goal/summary.json").read_text())
for key in ("mode", "seed", "success", "steps", "model_calls", "error"):
    print(f"{key}: {summary[key]}")
assert summary["mode"] == "scripted"
assert summary["model_calls"] == 0
assert summary["success"] is True
PY

然后回看 events.jsonl 的最终观察。尝试用自己的话描述验收需要的信息：方块是否仍附着在末端，方块与目标区域的相对位置是否满足环境定义。具体容差以实现中的验收函数为准，不能在报告里自行放宽标准。

第四步：先写验收，再看轨迹

给自己设一个小规则：阅读运行记录前，先写下成功条件。例如“红色方块被释放并处于当前蓝色区域的允许范围内”。读完事件记录后，只按这条规则判断；不要因为机器人动作看起来合理就改成成功。

这会暴露两类常见问题。第一类是目标解释错了，后续动作都围绕错误对象展开。第二类是目标正确，但执行失败，例如抓取没有建立或释放在旧位置。两类问题应分别归因，不能统称“模型不够聪明”。

SayCan 将语言层面的任务相关性与技能在当前环境中的可行性结合起来选择技能。它提醒我们，理解用户想要什么与判断机器人现在能做什么，是需要连接的两个环节。本章只实现有限目标解析与规则控制，没有训练 SayCan 的可供性模型。原项目与论文

本章验收与失败排查

检查项 应提供的证据
明确指令被接受 parse-goal 的完整输出
缺少信息不会被悄悄补齐 needs_clarification 结果与澄清问题
不存在的对象不会被替换 绿色方块指令的输出
执行完成了目标 独立验收结果与最终状态

如果本应澄清的句子被接受，先缩小解析规则，不要靠增加运动动作补救。对于否定句、多对象比较、先后顺序等超出当前语法的表达，使用解析命令检查边界，不直接交给机器人执行。若明确指令解析正确却搬运失败，回到第 6 章按工具反馈定位原因。

从展厅看更复杂的目标

打开 RoboMME：数清次数，再按下结束按钮。这里的成功条件依赖事件次数，单看最终一帧往往不够。写下“完成第几次”需要保留什么历史，再比较本章仅依赖当前状态的放置任务。

这个案例用于理解目标表示为何会扩展到时间与记忆。当前单方块实验没有实现 RoboMME 的任务集，也没有通过它的完整评测。

练习与参考

基础题：整理六条指令，分为支持、需要澄清、当前不支持三类，保存实际解析结果。进阶题：为“按顺序放置两个物体”写一个目标结构草案，并指出需要新增哪些场景实体和验收信息；先完成设计，不宣称当前代码已经支持。
